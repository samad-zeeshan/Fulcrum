It is registration week, and nobody can tell you whether this plan graduates you

A student sits with the course calendar open and five terms sketched out on paper. Every course on the page looks right. The rules are spread over a dozen pages, they overlap, and a few of them cancel each other out.

The advising office can answer, in three weeks, once the queue clears. Registration opens on Monday. So the student registers, and finds out in the final year that one line of the degree was never filled.

This plan does not graduate you, and here is the place it leaves empty

      Each course pays for one line, and one line only

      Three things you can see happen in the run above.

      • No course is counted twice

        A checker that tallies each requirement on its own would pass this plan, because CMPUT 402 counts toward both senior lines when you look at them one at a time. You watched it get spent on one of them. That is why a place was left open. planner/matching.py

      • It reports everything wrong, not the first thing

        All five checks run, and every failure is collected before anything is printed. A student fixing one problem does not have to run it again to find out about the next one. planner/validate.py

      • The same plan gets the same answer tomorrow

        The checker refuses to run against the live website at all. It reads a dated copy of the timetable, so a verdict can be repeated, argued with, and checked by somebody else. planner/snapshot.py

      It cannot build the plan for you, and it measured exactly how badly

      What this does not do

      Written down here so that nobody has to find it out later.

      • It cannot write you a plan. Four of the 47 questions asked for a course plan to be built from scratch. All three setups scored 0.0 out of 1 on those four. The plans came back looking sensible, and the checker rejected every one of them. Fulcrum can tell you that a plan is wrong. It cannot yet tell you what to take. reports/results.json, quality_by_type.plan_construction, all three setups
      • It knows one degree, for one year. The Computing Science major for the 2026 to 2027 calendar, and nothing else. Only 31 courses have a prerequisite rule (what you must take first) that a person checked by hand, so a plan built out of courses beyond that set gets a warning instead of a verdict. eval/gold/cs_major.gold.yaml
      • The timetable is a photograph, taken on 2026-06-28. It lists four terms, spring 2026 through winter 2027. Any later term in a plan is judged on which season the course usually runs in, rather than on a real timetable, because no real timetable for those terms exists yet. eval/snapshots/2026-06-28/offerings.json

      Six pieces, and the file each one lives in

      In order, from the university's website to the verdict on this page.

      1. A reader visits the university's course pages and saves them, then a second pass turns the saved pages into 954 plain course records. fetch.py, parse.py
      2. One dated copy of the timetable is frozen and never touched again, so the same plan always gets the same verdict. eval/snapshots/build_snapshot.py
      3. The degree rules are typed up by hand from the calendar. Every prerequisite sentence is kept word for word, so the checker can quote it back at you. eval/gold/cs_major.gold.yaml
      4. The checker runs the first four checks over a plan: nothing counted twice, nothing that cancels out, nothing sitting in a term it does not run in, nothing taken before what it needs. planner/validate.py
      5. Then the fifth, which is the hard one. It hands every course to at most one requirement line and searches for the arrangement that leaves the smallest gap. That is the step the board on this page draws. planner/matching.py
      6. A separate half answers written questions, and a marker grades those answers against the same rules the checker uses. eval/metrics/harness.py, eval/metrics/grade.py
